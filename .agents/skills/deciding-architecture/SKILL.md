# 構成の決め方

構成と判断の正本は `docs/architecture/overview.md`。`docs/plans/` は経緯の記録で、構成が食い違ったら overview.md に従う。

| 場面 | 見分け方 | 手順 |
| --- | --- | --- |
| 初回 | overview.md の「判断の記録」が空で、土台を作る、新しい種類の I/O を足す、構造を変える、のどれかをする(アプリのコードがすでにあっても) | [1](#1-初回) |
| 新しい種類の I/O | overview.md の原則で層にする種類の I/O のうち、overview.md の「層と入口」にないものを足す(設定ファイルの binding で足す場合も含む) | [2](#2-新しい種類の-io) |
| リアーキテクト | 構造を変える相談を受けた、または層と入口に反しないと実装できない | [3](#3-リアーキテクト) |

- どの行にも当たらない変更(ドキュメントだけの変更、I/O を増やさない設定の変更、構成に収まる機能の追加など)では使わない。

## 1. 初回

1. 承認を得るまで、overview.md と `docs/plans/` 以外のファイルは作らない・変えない。
   - アプリのコードがすでにある場合(テンプレートから来たファイルは含めない)は、今の構成を書き起こし、それを推奨案として 4 で示す。プランと食い違う点は 3 と同じく扱う(変えない案も示し、移すときは 3 の 3 に従う)。2 の「蒸し返さない」より、こちらを優先する。
2. プランを渡された場合(チャットに貼られたものも含む):
   - 中身が見えないときは貼ってもらう。
   - 保存し overview.md に写す前に、Secret・個人情報・公開できない情報がないかを確かめる。あれば、伏せる箇所をユーザーに確認する(公開リポジトリでは、コミットしたプランは履歴から消せない)。
   - 伏せた箇所のほかは要約せずに、`docs/plans/YYYY-MM-DD-<名前>.md` に保存する。
   - 決まっている構成は、伏せた箇所を除いてそのまま overview.md に写し、蒸し返さない。[原則](#原則の初期値)と食い違う点は、写したうえで 1 行で伝える。
   - 決まっていない点だけを相談する。
3. プランがない場合は、作るもの、外部とのやり取り、実行環境、テストの方法のうち、わからないものだけをまとめて 1 回で聞く。
4. [案の出し方](#案の出し方)に従って案を示し、承認を得る。示した推奨案への同意も承認として扱う(6 には当たらない)。
5. 承認を得たら、overview.md の原則・構成・判断の記録(1 件目)を書いてから土台を作る。決めた構成で使わないテンプレートの部品があれば、README で使わない部品と外し方を並べた節(番号付きの手順ではない)に従って外す。README がすでに書き換えられていれば、最初のコミットの README(`git log --reverse` で探す)を見る。
6. 案を示す前に、ユーザーが相談なしで始めるよう言った場合は、推奨の 1 案で 5 を行う。プランを渡されていれば、2 の確認と保存は省かない。判断の記録には「試作として決めた。本格化するときに見直す」と残す。

## 2. 新しい種類の I/O

既存の層の形を変える必要があれば、この節ではなく 3 に進む。それ以外は、overview.md の原則に沿って層を 1 つ足し(フレームワークが置き場所を決める箇所は、例外として「層と入口」の表に書く)、overview.md の「層と入口」と守り方を、コードと同じ PR で更新する。判断の記録にも 1 行残す。

- 既存の層と同じ形で済むなら、案は出さない。
- 初めての層を足すとき、または既存の層と違う形にするときは、[案の出し方](#案の出し方)に従って案を示し、承認を得る。判断の記録には退けた案も書く。

## 3. リアーキテクト

1. 勝手に変えない。lint の無効化コメントや再エクスポートで回避しない。
2. 「変えない」を含めて案を示し、承認を得る。ユーザーが変え方を指定した場合は、overview.md の差分だけを示して確認する。
3. 判断の記録を書いてから、コードと守り方(lint など)を同じ PR で移す。古い判断は消さず、「YYYY-MM-DD の判断で置き換え」と書き添える。

## 案の出し方

- 戻すのに手間がかかる点、またはトレードオフが本当にある点は、2〜3 案をトレードオフと一緒に示す。案は層の分け方と、それに効く技術選定で立てる。
- 自明な点は、採用案と理由、退けた案を 1 行で済ませる。
- 今決めなくてよい点は、overview.md の「後で決めること」に回す。

## 原則の初期値

初回に overview.md の「原則」へ写し、プロジェクトに合わせて直す。

- 層にする I/O は、費用・Secret・データの持ち主・テストのしにくさに関わるものだけにする。その種類の I/O が初めて出たときに、層(ディレクトリと、入口のモジュール 1 つ)を作る。
- I/O の手段(接続・binding・クライアント・Secret)は層の外に渡さない。層の外からは入口だけを使う。
- 守り方は、言語の可視性(Go の `internal/`、Rust の `pub(crate)` など)、lint、テストかレビュー、の順に選ぶ。
  - lint のメッセージには、代わりに使う入口を書く。
  - 違反を 1 件置いて、lint が落ちることを確かめる。
  - 捕まえられない書き方は、overview.md の「層と入口」に書く。
- フレームワークが I/O の置き場所を決めている箇所は例外とし、理由と一緒に「層と入口」の表に書く。
- interface と抽象化は、2 つ目の実装(Fake など)が必要になってから作る。
