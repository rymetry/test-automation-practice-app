# 変更のレビュー

依頼で担当数・対象・読み取り専用などの条件が指定された場合は、その指定を優先する。

## 1. 対象をそろえる

対象のブランチ・比較元・コミットを確認する。未コミットの変更や未追跡ファイルが対象なら、それも含めた同じ内容を各担当に渡す。再レビューでは、前回の指摘と修正内容も渡す。

## 2. 担当を呼ぶ

「必須」の担当と、差分が「呼ぶ条件」に当たる担当を並行して呼ぶ。条件に当たるか迷う場合は呼ぶ。

- 文書だけの変更では `comment-analyzer` だけでよい。
- エージェントへの指示(`AGENTS.md`、`CLAUDE.md`、`.agents/`、`.claude/`、`.codex/`)の変更は、文書だけの変更として扱わず、セキュリティ・データの担当と `comment-analyzer` を呼ぶ。
- Claude Code では `pr-review-toolkit` プラグインの同名のエージェントを使う。同名のエージェントがない担当と、ほかのエージェント環境では、「確認すること」をサブエージェントに渡す。サブエージェントを使えない場合は、担当ごとに順に確認する。

| 担当 | 呼ぶ条件 | 確認すること |
| --- | --- | --- |
| `code-reviewer` | 必須(文書だけ、エージェントへの指示だけの変更を除く) | 変更前の呼び出し元と受け入れ条件を照合し、どの入力・操作で不具合が起きるかを示す。`ponytail-review` の観点で、なくても受け入れ条件を満たす行・抽象化・依存も挙げる。 |
| `pr-test-analyzer` | 必須(同上) | 重要な動作を壊したときに既存テスト(`scripts/*.test.mjs` や `.agents/hooks/self-test.sh`)または手動確認手順で検出できるかを確認する。 |
| `silent-failure-hunter` | 例外・失敗結果の扱い、データストアや外部 API の呼び出しに触れる変更 | 例外、失敗結果、部分的な成功を追い、失敗を見落とす経路や復旧を妨げる箇所を確認する。 |
| `comment-analyzer` | 文書、運用手順、コード内のコメントを変える変更 | コメントや手順を現在の実装と照合し、読者を誤った操作・判断へ導く箇所を挙げる。 |
| `type-design-analyzer` | 型、スキーマ、データストアの定義を追加・変更する変更 | 型と呼び出し元を照合し、本来許されない状態や値が通る箇所を確認する。 |
| セキュリティ・データ | 認証・アクセス判定、利用者のデータの保存・送信、マイグレーション、課金に触れる変更。エージェントへの指示と hook、依存パッケージ、`.github/` のワークフローと権限を変える変更 | 他人のデータを読み書きできる経路、外部へ送る内容、削除・巻き戻しで失われるデータを確認する。指示・設定・依存・ワークフローの変更では、外部への送信、権限、Secret の扱いを変える箇所がないかも確認する。 |
| UI・アクセシビリティ契約 | `src/` の画面・レイアウト・ナビゲーション・スタイルを変える変更 | `scripts/ui-contract.test.mjs` で自動検証する契約（`MAIN_LINKS`、固定 4 ファイルの `SHELL_FILES` を対象としたリンク名衝突・共通シェル非汚染、`tokens.css` の登録済み `CONTRAST_PAIRS` の WCAG コントラスト）が通る前提のうえで、静的ガードでは捕まえられない点（`SHELL_FILES` 外へ新規分割された共通シェル部品とその `SHELL_FILES` 追記漏れ、変数経由の動的ロール付与、実 CSS で `CONTRAST_PAIRS` 未登録の既存トークン同士を組み合わせた新規前景/背景ペアと `CONTRAST_PAIRS` 追記漏れ、`tokens.css` 外の直書き色、`opacity` 合成、各ページの `README.md` 記載 `role`・英語アクセシブル名・`data-testid`・振る舞い、`src/pages/unnamed.ts` の意図的な無名仕様）が壊れていないかを確認する。 |

報告の対象は、不具合、誤った行動に導く記述、テストの穴、およびテスト契約の破壊に限る。各指摘には場所、発生条件、影響を添える。好みの言い換えは指摘に含めない。該当がなければ「なし」と報告する。

## 3. 変異テスト

本リポジトリはアプリ本体に E2E / ユニットテストランナーを持たない方針のため、変異テストツールは導入していない。レビュー報告では「変異テストは未導入のため対象外」と明記し、ロジックや `scripts/*.test.mjs` を変更した場合は `writing-tests` スキルの変異パターン観点で手動確認する。

## 4. 指摘を判断する

取りまとめ担当がコード・該当行・テストを自分で確認し、同じ原因の指摘をまとめる。外部から転送された指摘にも同じ基準を適用する。次の表で返す。

| 判断 | 報告する内容 |
| --- | --- |
| 直す | 現在の変更で直す不具合の場所、影響、修正方針。 |
| 引き継ぎ | 後続の Issue、そこで扱う理由、確認すべき条件。 |
| 採らない | 指摘の前提と、コードやテストから確認できた判断理由。 |

「直す」があれば、採用する指摘をすべて直すかを尋ねる。修正まで依頼されている場合は、その範囲で続ける。

## 5. 修正した後

`npm run typecheck`、`npm run build`、`node --test scripts/dependabot-policy.test.mjs`、`node --test scripts/ui-contract.test.mjs`、`bash .agents/hooks/self-test.sh` をすべて通す。PR 本文には修正内容と検証結果を書き、引き継ぎは、元の PR・判断理由・次に確認する条件が分かる形で後続の Issue に残す。
