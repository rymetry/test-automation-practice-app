# テストコードの書き方

テストの役割は、コードが壊れたときに失敗すること。コードを実行するだけで結果を検証しないテストは、カバレッジを上げても不具合を検出しない。

このリポジトリではアプリ本体に E2E テストを持たず、運用スクリプトや契約ガードのテストを Node.js 標準の `node --test`（`scripts/*.test.mjs`）、hook の検証を `bash .agents/hooks/self-test.sh` で行う。書いたテストごとに、対象のコードへ次の変更(変異)を入れたら失敗するかを確かめる:条件を反転する、境界を 1 ずらす、処理を 1 行消す、足している項を 1 つ落とす。

## 原則

1. **観測できる振る舞いを検証する。** 戻り値、投げられるエラー、保存された状態、外部への呼び出しとその引数を見る。
2. **境界は、ちょうどの値と隣の値の両方を入力にする。** 閾値から遠い値だけでは、`>=` と `>` の違いを検出できない。
3. **厳密に比較する。** 真偽や部分一致ではなく、値・件数・並び順を完全一致で見る。
4. **通る場合と拒否される場合を対で書く。** 拒否は、その検査に固有の理由(エラーコードやメッセージ)まで照合する。
5. **起きてはならないことも検証する。** 拒否した後に副作用がない、出さない条件で表示されない、件数が増えていない。
6. **フィクスチャの値を互いに区別できるものにする。** 0、空、たまたま同じ値を使うと、項の脱落や取り違えが結果に現れない。
7. **実装の内部を固定しない。** 非公開の状態、内部の呼び出し順、テスト対象自身のモックに依存したテストは、変異は検出してもリファクタリングで壊れる。
8. **テストを通すために対象のコードを変えない。** 不具合を見つけたら報告し、確認を取ってから直す。
9. **テスト名は、検証する振る舞いを表す。**

## 書いた後に確かめる

- 表やループで回すテストは、対象が 0 件でないことを先に検証する(空回りで通るのを防ぐ)。
- 期待値の一覧をテストに写さない。設定ファイルなど、もう一方の正から読み出して照合する。
- 文言の完全一致は、利用者に見える文か、値の受け渡しを守る目的に限る。

## 変異の観点

- 生き残りやすい変異の型と、検出するテストの書き方:[references/mutation-patterns.md](references/mutation-patterns.md)
- 本リポジトリでは自動変異テストツールを導入していないため、`scripts/*.test.mjs` を追加・更新するときは上の型に沿って手動で抜け漏れを確かめる。
- どの入力でも結果が変わらない等価な変異は、実装の内部を固定するテストで無理に落とさない。等価と決める前に、上流の検査が違いを隠していないかを確かめる。
